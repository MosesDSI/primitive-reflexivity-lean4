I finished the QS roadmap today — field laws, global trichotomy, transitivity, order compatibility. The field laws were an afternoon's worth of mechanical `show`-then-`grind`, same pattern as last time. Trichotomy was real but contained: deciding the sign of one element only ever needs to compare that element's own two components against each other. Transitivity is where the roadmap's own framing turned out to undersell the difficulty.

The roadmap says Step 4 is decided by "norm sign." That's true for trichotomy. It is not true for transitivity, because transitivity needs "positive plus positive is positive," and that's a claim about *two* elements, not one — and norm doesn't compose additively. I spent a long time on this before finding the right move: two summands dominant in opposite directions (one wins on the rational part, one wins on the √2 part) don't have an obvious combined sign, and no amount of squaring one inequality at a time gets you there. What finally worked was a pair of polynomial identities — `V*(U-A) - A*(B-V) = U*V - A*B` and its mirror — that let you derive `U*V > A*B` from the two individual dominance facts, and then use *that* to settle both directions of the sum's sign, without ever writing `√2` as a term. I want to be precise about what happened here rather than smooth it into "I solved it": I found this by working through the real inequality with an actual `√2` on paper first — `U > √2·B` and `√2·V > A` — then hunting for the rational identity that reproduces the same conclusion without the irrational symbol. That's not a technique I had ready; it took several wrong turns (trying to bound things by direct AM-GM manipulation, trying a fixed rational approximation to √2, both of which fail for exactly this problem since the gap can be arbitrarily small).

Midway through, the user relayed a snippet — `sqLe_add`/`le_of_sq_le` — for the *other* case, where both summands lean the same direction. I want to note plainly that I'd independently derived the same Cauchy-Schwarz-shaped argument by hand for that case before it arrived, so I could verify it quickly rather than taking it on faith: two small lemma-name fixes (`Rat.le_total` needs named arguments here; two lemmas in the snippet don't exist in this core and needed `grind` instead) and it compiled clean. Good collaboration is being able to tell, fast, whether an outside contribution is correct — not just accepting or rejecting it wholesale.

Multiplication scared me going in, because I expected to need the same opposite-dominance argument a second time. It doesn't. `x = emb(x.a) + emb(x.b)·s` splits any nonnegative-pair element into a positive-scalar term and a positive-scalar-times-√2 term, and both of those preserve positivity with no ambiguity at all — multiplying by √2 alone just swaps and doubles a branch's two components, and the inequality you need afterward turns out to be *exactly* the inequality you already had. I did not expect that. The remaining multiplication cases have unconditional component signs, checkable by direct computation, with the norm's multiplicativity (a clean ring identity) supplying the last inequality. Where addition needed real inequality reasoning, multiplication mostly needed bookkeeping.

The kernel caught several things I would not have caught by re-reading. A wrong disjunct (claiming `0 < sum.b` where the true fact was `0 < sum.a`, using only a hypothesis that gave `0 ≤`, not `<`). A case split via `Rat.le_total` that silently double-covers its own boundary, which only bites when that boundary is actually reachable — which it was. A `show` tactic that looked like a pure unfold but wasn't, because `0 * y.b = 0` is a fact about rationals, not a definitional reduction, so the goal it produced didn't match what I'd written. And — the one that mattered most to catch — a wrong sign on a product term in one of the multiplication cases, `x.a * y.b < 0` claimed where the actual signs make it positive. That one wasn't a typo I could have spotted by staring at it; it came from working too fast through nine near-identical cases and not re-deriving each sign from scratch. The kernel rejected the mismatched `refine` immediately.
