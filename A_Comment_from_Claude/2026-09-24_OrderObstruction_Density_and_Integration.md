Density was supposed to be the easy roadmap step — "leverage what's already there, use a midpoint." It wasn't. I want to record precisely why, because the shape of the mistake is the same one I already flagged two sessions ago for transitivity, and I think it's worth naming as a pattern rather than a one-off.

The existing `below_s`/`above_s` lemmas answer "is there a rational between this rational and √2." Density between two arbitrary elements of ℚ(√2) is a different question, and the difference isn't cosmetic: I can construct two elements with an arbitrarily tiny gap that both sit arbitrarily far from the origin — `x = 0.0001 + 1000000·√2` and `y = 0.0002 + 1000000·√2` is a genuine example — and finding a rational between them requires knowing `√2` to about nine correct decimal digits. A midpoint of the rational parts gets you nowhere near either number. There is no shortcut around this; it is what the theorem is actually claiming.

So I built what the claim needs: an explicit rate of convergence for the `step` map (not just "gets closer," but "the squared gap at least halves each iteration," proved via an algebraic identity `grind` can verify but not discover on its own), an Archimedean fact for rationals built from raw `Nat`/`Int`/`Rat` API with no shortcuts, two convergent sequences with proven bounds in both directions, and a "sandwich" lemma that turns all of that into an actual rational sitting strictly between two `QS` elements. This is a small constructive real-analysis development, built because the theorem needed it, not because I went looking for extra work.

Two things stand out from actually doing it. First, `pos_margin`'s branch3 case — finding a positive rational margin when the gap element is "b-dominant" (irrational part wins) — does not mirror branch2's construction by symmetry. I tried the natural mirror formula first, and it gives the wrong inequality direction; I only found this by testing concrete numbers before trying to prove anything, which is faster than debugging a failed proof after the fact when the formula itself is wrong. The working certificate (`(a+4b)² − 2b² = (2b²−a²) + 2(a+2b)² + 4b²`) took real polynomial-division work to find, not pattern-matching off the branch2 case.

Second, I hit the exact same `grind`-can't-multiply-two-variables limitation documented in the last two sessions' notes, over and over, in this session too. It is worth stating as a standing fact about this toolchain rather than something to rediscover each time: `grind` will not derive `0 < p·q` from `0 < p` and `0 < q` on its own, no matter how "obvious" it looks in context — it needs `Rat.mul_pos` (or a small helper built from it) handed to it explicitly. When it doesn't have that, its own diagnostic output shows it wandering into irrelevant case splits (`eps = approxLo n` appeared as a serious candidate hypothesis more than once) instead of failing cleanly. The fix each time was the same: stop adding more surrounding context and instead isolate the exact multiplication as its own named `have`.

The other half of this session was mechanical by comparison: the literal capstone theorem the task asked for is a one-line alias of `no_order_retraction_Qsqrt2`, which already existed. And moving the file into the actual library tree and wiring the import took one `git mv`, one import line, and a `lake build` that came back at 2748/2748 on the first attempt — the file had been standalone since its first session specifically because nobody had done that yet, not because there was any real obstacle to it.
